01 · ArchitectureThe map before the streets

What kind of system is this?

The reviewed codebase is a modular TypeScript backend. It keeps major healthcare and business domains separate inside one deployable product, while using asynchronous infrastructure for work that should not block a user-facing request.

RuntimesHTTP API, scheduled jobs, batch jobsUser requests, recurring work, and heavy offline work run through different entry points.

Why a modular monolith can be a good choice

It keeps deployment and transactions simpler than dozens of independent microservices, while still forcing clear module boundaries. A team can later extract a high-scale or independently owned module if the cost is justified. “Monolith” does not automatically mean “messy.”

03 · API designA contract between products and systems

An API is more than a URL.

A complete API design defines the actor, input, validation, allowed state, business decision, durable write, response, errors, duplicate behavior, side effects, and instrumentation.

Example: book an appointment

Request: patient, slot, journey context, source, idempotency key. Decision: patient is eligible and slot remains available. Response: confirmed booking reference and current state. Side effects: reminder timer, provider calendar, confirmation message, operations visibility, and analytics event.

Weak specification

“Create a booking API and send WhatsApp.”

Strong specification

Defines duplicate calls, slot races, rejected states, timeout behavior, committed truth, retry ownership, and the funnel event.

04 · State machines & eventsMemory plus a clock

State says where. Events say what happened.

A state machine names valid stages and transitions. A domain event records a meaningful fact. A scheduled event makes future work durable. A queue lets consumers perform side effects without blocking the customer.

ConceptQuestion it answersExample
StateWhere is this entity now?Appointment is booked; fulfilment is dispatched.
TransitionIs this change allowed?Booked → completed is allowed after the consultation; cancelled → completed may be blocked.
Domain eventWhat important fact just occurred?appointment.completed; invoice.confirmed.
Scheduled eventWhat must happen later?Send reminder tomorrow; make repeat journey eligible after a window.
ConsumerWho reacts to the fact?Messaging, task creation, payout ledger, analytics, or a partner webhook.
05 · Schema designHow the business becomes data

A schema is the product’s memory structure.

Tables and relationships should make customer state, operating work, financial outcomes, and history easy to trace. A clean schema prevents every dashboard or feature from inventing its own definition of truth.

Entity

A thing with its own identity: person, appointment, order, payout ledger item.

Relationship

A stable link: an appointment belongs to a journey episode; a payout references its source.

Index

A structure that makes common lookups fast, such as active tasks by owner or appointments by patient.

Product rule of thumb

Use explicit columns and relationships for concepts that drive product logic, money, permissions, or reporting. Use JSON for genuinely flexible metadata—not to avoid deciding what the core product entities mean.

06 · Reliability patternsAssume retries and partial failure

“Exactly once” is a product behavior, not a wish.

Distributed systems repeat requests, lose connections, deliver messages late, and fail after one side effect but before another. Reliability patterns make the intended business outcome happen once—or make the exception visible.

Idempotency

Repeating the same request produces the same business outcome. Essential for bookings, ledger entries, payments, tasks, and outbound messages.

Lock

Temporarily prevents two actors from claiming the same scarce resource, such as an exact appointment slot.

Outbox

Stores a future event durably with the transaction so scheduled work is not lost if the process restarts.

Retry tiers

Transient failures are attempted again after increasing delays so a partner outage does not block the main request.

Dead-letter queue

Work that exhausted retries is retained for investigation or replay instead of disappearing silently.

Audit history

Records actor, request, previous state, next state, and time so teams can explain what happened.

Failure walkthrough: confirmation message fails

  1. The booking transaction commits successfully and returns a booking reference.
  2. A booking-created event is published or placed in a durable outbox.
  3. The messaging consumer attempts delivery; the external provider times out.
  4. The queue retries. Idempotency prevents a duplicate successful send.
  5. After exhausted retries, failed work reaches a dead-letter path and an alert or operations view.
  6. The booking remains true; only the notification side effect needs recovery.

08 · Journey examplesChatbot, tasks, payout, fulfilment

Different domains reuse the same primitives.

AI chatbot and escalation

Flow: inbound message → conversation history → intent/classification → response or escalation → task/callback → outcome event.

Controls: rate limits, URL/input sanitization, human review, escalation thresholds, traces, quality sampling, and conversation-level attributes.

Calling-task deduplication

Flow: journey event → objective and priority rules → existing-task lookup → expire/merge/create → carry forward context.

Controls: stable patient/objective keys, latest relevant context, explicit expiry, owner visibility, and workload metrics.

Doctor payout platform

Flow: contract + rule version → source business event → calculation → ledger entry → approval → statement/payslip → payment initiation.

Controls: unique source reference, slab and validity rules, append-safe adjustments, role-based approval, audit trail, and reconciliation.

Order fulfilment

Flow: pending → address confirmed → packed → dispatched → out for delivery → delivered, return, or cancellation.

Controls: valid state transitions, partner reference, webhook deduplication, exception visibility, and event-driven customer communication.

The reusable pattern

Identify the entity → define its states → specify allowed commands → commit durable truth → publish events → execute side effects idempotently → trace every outcome → measure the customer and business result.

Why this matters for fintech

The same mechanics power loan applications, mandates, repayments, settlements, partner commissions, trade orders, portfolio rebalancing, and collections: explicit states, auditable money movements, idempotent commands, asynchronous side effects, and strong observability.

09 · ObservabilityKnow what happened before customers tell you

Logs are not the same as product understanding.

Observability connects technical evidence to journey evidence. Datadog or tracing can explain latency and errors; product analytics explains whether users progressed; business metrics explain whether the operating model worked.

System healthCan it execute?

Latency, error rate, queue age, retry count, duplicate rate, lock contention.

Journey healthDid the user progress?

Eligibility, conversion, drop-off reason, completion, turnaround time, exception rate.

Business healthWas it valuable?

Repeat revenue, LTV, payout cost/revenue, workload, margin, service quality.

Log

A timestamped record from one component: “validation failed” or “consumer retry 2.” Useful, but fragmented.

Trace

Follows one request or event across components using a shared request/trace ID, revealing where time or failure occurred.

Metric

A count, rate, duration, or gauge observed over time: errors/minute, queue age, completion rate, or weekly tasks.

Alert

A rule that calls attention to a meaningful threshold. Good alerts are actionable and tied to an owner and runbook.

A product-ready monitoring brief

  1. Name the business-critical command and its service-level expectation.
  2. Attach request ID, actor type, entity ID, source channel, outcome, error class, and latency.
  3. Define leading funnel events and one source of truth for the final business outcome.
  4. Alert on both system failure and silent journey failure, such as a healthy API but zero confirmations sent.
  5. Document manual recovery, replay safety, communication owner, and the metric used to close the incident.

11 · Interview practiceAnswer from problem to production

Use one repeatable answer structure.

01

Business problem

Baseline, user pain, operating constraint, and why it mattered.

02

System contract

Entities, states, actors, API/event behavior, and failure paths.

03

Delivery

Trade-offs, ownership, collaboration, rollout, and manual fallback.

04

Evidence

System, journey, and business metrics; what changed afterward.

Practice questions

  1. How would you prevent two patients from booking the same slot? Discuss fresh availability, short-lived hold/lock, transactional booking, unique constraint, idempotency, and a clear “slot no longer available” response.
  2. Why use an event instead of calling every system synchronously? Explain response latency, partial failures, independent consumers, retries, and the need for durable delivery and idempotency.
  3. How would you model repeat care? Describe a journey episode, current state, transitions, scheduled eligibility, related appointments/orders/messages, and event history.
  4. How would you design payout data? Separate contract/rule version from append-safe ledger entries, approvals, payslips, transaction references, audit events, and adjustments.
  5. How do you know a chatbot works? Combine model/trace quality, containment, escalation correctness, next-action completion, self-booking, repeat contact, and customer outcome.
  6. What belongs in a PRD for an API-heavy feature? Actors, journey states, functional contract, edge cases, idempotency, errors, events, integration ownership, observability, migration, rollout, and support plan.
The interview habit to build

Never stop at the happy-path screen. Always add: current state, source of truth, duplicate call, timeout, partial failure, customer message, operator visibility, audit trail, rollout guardrail, and success metric.

12 · GlossaryPlain-language reference

The technical terms you should own.

API
A structured contract that lets one product or system request data or an action from another.
Endpoint
One address and method within an API, such as creating a booking or fetching availability.
DTO
A typed request/response shape that defines fields and validation at the API boundary.
Authentication
Proving who the actor is. Authorization separately decides what that actor may do.
Webhook
An HTTP callback sent to another system when a relevant event occurs.
Entity
A business object with its own stable identity, data, and lifecycle.
Schema
The structure, fields, relationships, and constraints used to store data.
Migration
A controlled, versioned change to database structure or data.
Index
A data structure that makes chosen database lookups faster.
State machine
A model of valid states and the allowed transitions between them.
Domain event
A durable business fact that other parts of the system may react to.
Queue
A buffer that holds background work until a consumer can process it.
Consumer
A worker that reads queued messages and performs one defined action.
Idempotency
The property that repeating a command does not repeat the business outcome.
Lock
A temporary control that prevents concurrent actors from changing or claiming the same resource.
Cache
A faster temporary copy of data used to reduce latency or repeated computation.
Outbox
A durable database record of an event that should be published or executed later.
Retry
Trying failed work again, usually after a delay, when the failure may be temporary.
Dead-letter queue
A holding area for messages that exhausted retries and need investigation or replay.
Observability
The ability to understand system behavior using logs, metrics, traces, events, and alerts.
Trace ID
A shared identifier that follows one request or event across components.
Feature flag
A switch that enables a change for selected users or traffic without a new code deployment.
Source of truth
The authoritative system or record used when multiple surfaces show the same concept.
Adapter
A translation layer that lets internal logic work with an external provider’s contract.
